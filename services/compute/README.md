# services/compute

Python FastAPI 계산 서비스다. 임베딩(multilingual-e5-small), 코드북 주소 발급, 테이블 배정, 커피챗 추천을 맡는다. 상태는 갖지 않고 결과는 Supabase 에 버전을 붙여 쓴다. 담당은 민찬이다.

## 로컬 실행

```bash
cd services/compute
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
copy .env.example .env          # 값 채우기
uvicorn main:app --reload --port 8000
```
- Intel 맥(x86_64)은 `pip install -r requirements-mac-intel.txt` 를 쓴다. 최신 torch 가 Intel 맥을 지원하지 않아 torch 2.2.2 · transformers 4.4x · numpy 1.x 로 고정한 목록이다(9/29 확인). 결과는 같다
- 서버는 .env 를 스스로 읽지 않는다. `set -a; source .env; set +a` 뒤에 uvicorn 을 띄운다(운영자 노트북)


`http://localhost:8000/health` 가 열리면 된다. Windows 에서 anaconda 와 torch 가 충돌하면 `set KMP_DUPLICATE_LIB_OK=TRUE`.

## 알고리즘 (`pipeline/`)

연구 저장소 `26-2_Modeling_RecSys/event_demo/06_event_loop.py` 의 발급 · 배정 · 추천을 옮겼다. DB 입출력 없이 배열만 받고 돌려준다.

| 파일 | 하는 일 |
|---|---|
| `embed.py` | 문장 → 벡터. 자유 문장을 항목으로 나눠 항목마다 벡터를 만들고 평균 |
| `codebook.py` | 공유 코드북(출처별 평균 제거), 주소 발급, 고정 코드북에 늦게 온 사람 붙이기, 구분 번호 |
| `scoring.py` | 한 방향 점수 a, 테이블용 결합(min · 평균 · 조화평균), 호스트 단방향, 만남 반영(G★ 주입) |
| `seating.py` | 호스트 먼저 → 한 명씩 → 담금질. 바뀐 두 테이블만 다시 세는 증분 계산으로 70명 2만 번 0.3초(원본 38초). 테이블토크 9테이블 균등(even_sizes, 2~10번. 10/21 민찬 결정) · 같은 기수 테이블당 3명(4명째부터 0.5 감점), 커피챗 3~4명 그룹(group_sizes), 좌석 순서(seat_order, 이웃 점수 합 최대를 정확히, 17명 이상은 근사) |
| `recs.py` | 개인 추천(정확 8 + 탐색 2 = 10명, 10/10 회의, 이미 만난 사람 제외, 노출 상한), 이유 칩, 테이블 대화거리 (테이블 이름표는 달지 않음) |
| `signals.py` | 반영 신호 정리(v0.2 B-05). 명함 교환 가중(첫 대화 1.0 · 그 밖 0.5 · 확인 대기 제외), 포스터 응답 가중 · 필터. 규칙 정본은 docs/DATA_SPEC.md |
| `evidence.py` | 커피챗 그룹 카드 근거 한 줄(B-07, 문장별 벡터로 찾는 사람 ↔ 하는 일 최근접, 기준 상위 30%), 테이블 · 그룹 라벨(B-08, 궤도 전용) |

시험은 `python tests/test_pipeline.py` (pytest 가 있으면 `python -m pytest tests -q`). 모델 없이 가짜 벡터 70명으로 돈다.

실제 모델로 한 바퀴는 `python sim/run_sim.py`. 가상 70명(템플릿 문장)으로 발급 → 테이블토크 → 명함 교환(합성) → 만남 반영 → 커피챗 → 추천까지 돈다. 맥 CPU 기준 모델 로드 9초, 임베딩 0.4초, 코드북 0.05초, 배정 라운드당 0.3초, 제약 위반 0. 주소 충돌 43~47% 는 템플릿 문장이 서로 비슷해서 생긴 것이다(연명부 시험의 49명 같은 문장과 같은 원인).

- 비교군: 무작위(1000회), 운영진 기수 규칙(연명부 2번 시트의 실제 수기 배정 방식), 운영진 태그 규칙, 알고리즘, 정답 기준 배정(참고)

### 추천 10명 점수 (10/18, `REC_SCORE=rule` 기본)

"오늘 만나면 좋을 분" 10명은 세 점수를 표준화해 1 : 1 : 2 로 섞은 **한 방향** 점수로 고른다(`scoring.rec_rule_score`).

1. 찾는 사람 → 하는 일 cos(평균 뺀 벡터)
2. 하는 일끼리 cos(평균 뺀 벡터, 같은 분야)
3. **'줄 수 있는 것' 규칙**(`scoring.WANTS`): 내가 고른 '개더링에 기대하는 점'(사전 등록 폼, 관계태그) 중 규칙이 있는 것마다 상대가 줄 수 있는 정도(1 또는 0.5)를 더해 그 개수로 나눈 값

| 폼 선택지(10/18 사전 등록 폼) | 줄 수 있는 상대(구분 = participants.careers 0017, 없으면 career 0015 · 0016) |
|---|---|
| 커리어 조언·현업 이야기 | 기업 재직 1, 기업 인턴 0.5 — 재직자보다 한 단계 낮게(민찬) |
| 취업·이직 정보 | 기업 재직 1, 기업 인턴 0.5 |
| 대학원 진학·연구 | 대학원생 · 교수 1, 학부연구생(연구실 인턴) 0.5 — 대학원생보다 한 단계 낮게(민찬) |
| 스터디·프로젝트 팀원 찾기 | 학생 · 학부연구생 |
| 최신 AI·데이터 트렌드 | 재직자 · 대학원생 0.5 |
| 창업·사이드 프로젝트 | 창업자 1(경험 '창업' · 외부연사 CEO), 같은 선택지를 고른 사람 0.5(같이 할 사람, 창업자보다 한 단계 낮게) — 10/19 민찬 |
| 비슷한 분야 사람 만나기 · 다른 기수와의 교류 | 규칙 없음(분야 점수가 맡음). 세지 않음 |

왜: 문장 비교 모델은 '재직자 → 취업 · 이직 정보' 같은 연결을 잡지 못한다(가상 80명 시드 20개에서 예전 점수와 필요 충족의 상관이 거의 0: 폼 조건 평균 0.03, 범위 −0.03~0.11. 10/19 다시 잼).
더 큰 모델도 9월 공동저술 확인에서 같았다(사람별 AUC, 영어 제목 기준 e5 0.712 · bge-m3 0.705 · KURE 0.707, 연구 저장소 docs/33). 그래서 규칙으로 직접 넣는다.
한 방향인 이유: 양방향 작은 쪽(min)이면 '학생은 선배에게 취업 정보가 필요하지만 선배는 학생에게 필요한 게 없는' 쌍이 0점이 된다.

`python sim/eval_recs_rule.py --seeds 2026-2045` (서비스 추천 함수 그대로 · 노출 상한 12 · 전날 동석자 제외, 시드 20개 평균, 추천 10명 중 좋은 상대 수)

| 방식 | 같은 분야 기준 | 관심 도메인 기준 | 좋은 상대 0명(같은 분야 기준) |
|---|---:|---:|---:|
| 예전 min(10/17 까지 기본) | 2.79 | 2.18 | 13% |
| 배정용 보정 점수 min | 2.90 | 2.30 | 12% |
| **rule** | **3.49** | **3.02** | **3%** |

(10/19 다시 잼. 사전 등록 폼에 찾는 사람 문항이 없어 서비스는 자기 하는 일로 대신한다(`fill_blank_seek`). 그래서 행사 전 추천은 찾는 사람 → 하는 일 점수 = 하는 일끼리 점수(실제로는 분야 1 : 규칙 1)이고, 평가도 찾는 사람을 비운다(`--seek blank`, 기본). 행사 중 재계산은 만족도 · 명함 · 포스터 · 검색으로 옮긴 찾는 사람을 써서 다시 1 : 1 : 2 가 된다.
10/18 처음 잰 2.60 · 3.01 · 3.52(관심 도메인 기준 2.86 · 2.88 · 3.82, 그때 규칙표)는 찾는 사람에 숨은 관심 도메인 문장을 넣은 것(`--seek interest`, 지금 규칙표로는 rule 3.54)이라 폼에서는 나오지 않는 정보가 들어갔다. 가상 정답의 원하는 것을 폼 선택지로 옮겨서 잼, 폼에 '채용' 선택지는 없음)
규칙표가 실제와 어긋날 때(`--noise`, 숨은 정답의 줄 수 있는 것을 항목마다 흔듦): 0.4 에서 rule 2.66 · 예전 2.24 · 보정 2.31 로 앞서고, 완전 무작위(1.0)면 2.47 · 2.45 · 2.53 으로 이득이 없어지고 보정보다 조금 낮다.

좌석 배정에는 규칙을 넣지 않았다. `python sim/eval_seat_form.py --seeds 2026-2045 --random 300` (테이블토크 → 커피챗, 행사 중 좋은 만남 1인 평균, 시드 20개)

| 찾는 사람 | 무작위 | 예전(0/0) | 배정용 보정(1/0.5) | 보정 + 규칙 | 보정 + DSL 활동 |
|---|---:|---:|---:|---:|---:|
| 빈칸(폼, 기본) | 1.62 | 1.65 | **2.03** | 1.94 | 1.93 |
| 숨은 관심 도메인(`--seek interest`) | 1.62 | 1.64 | **2.13** | 2.00 | 2.05 |

- 규칙 · DSL 활동(하는 일에 'DSL 활동: …' 줄)을 더하면 보정보다 낮다(보정보다 나은 시드 5/20 · 7/20). 그래서 좌석은 보정 그대로, DSL 활동 문항은 계산에 안 쓴다
- 선배가 많아(실제 명단 81명 중 수료기수 53명) 무작위로 앉혀도 어려운 필요(취업 · 이직 정보 · 멘토링 · 대학원 진학 · 채용 · 연구 협업 · 창업)가 있는 사람의 98% 가 그걸 줄 사람을 만난다. 추천은 80명 중 10명을 골라야 해서 규칙이 차이를 낸다
- (10/18 스크래치 실험의 1.73 → 2.12 · 2.07, DSL 2.55 → 2.27 은 찾는 사람에 관심 도메인을 넣고 10/17 폼 모양 · 예전 규칙표로 잰 값. 위 표로 바꿈)
한계: 규칙표가 가상 데이터 정답표(단계별 줄 수 있는 것)와 일부 겹친다. 가상 평가의 구분은 사람마다 하나(재직 · 대학원 · 학생 · 교수)라 기업 인턴 · 학부연구생 · 창업자 · 여러 구분은 아직 재지 않았다. 가상 정답에 '트렌드' 필요가 없어 최신 AI·데이터 트렌드 규칙(0.5)도 재지 않았다(정답을 규칙표대로 만들면 스스로 맞히는 셈이라 리허설 · 행사 데이터로 본다). 실제 효과는 리허설 · 행사의 교환 · 만족도로 다시 본다.
구분은 사람마다 여러 개일 수 있다(0017 careers: 폼 '해당하는 경험을 모두 골라 주세요'의 기업 재직 · 기업 인턴 · 창업 · 학부연구생 · 대학원 + 재학생 · 교수, 기타(외부연사 CEO)는 재직자 + 창업자). 선택지마다 그중 가장 높은 값을 쓴다. 경험이 여럿이어도 같은 정보를 두 배로 줄 수는 없어서 더하지 않는다.
예) 기업 인턴을 해 본 학부연구생 재학생 → 취업 · 이직 정보 0.5 · 대학원 진학 0.5 · 스터디 1.
구분을 아무도 모르거나(0015 전 DB, 예전 명단) 아무도 규칙 있는 선택지를 안 고르면 예전 min 으로 돌아간다. 폼 '기대하는 점' 선택지가 바뀌면 `WANTS` 의 말도 같이 바꾼다(모르는 선택지는 params.intent_unknown).

### 06_event_loop.py 와 다른 점

연구 저장소의 대리 확인 결과(docs/31 · docs/33, 노션 9/23 백엔드 구현 결정)를 따라 바꿨다. 회의에서 다르게 정하면 설정값만 바꾸면 된다.

| 항목 | 원본 | 여기 | 근거 |
|---|---|---|---|
| 접두사 | passage: | query: (`EMBED_PREFIX`) | e5 설명서상 대칭 비교는 양쪽 query:. 한 방향 점수에서 passage: 가 나은지는 아직 비교 안 함 |
| 점수용 벡터의 평균 제거 | 함 | 추천 · pair_scores 원본은 안 함, 테이블토크 · 커피챗 배정은 함 | 평균을 빼면 AUC 0.78 → 0.70(공동저술 대리 확인). 배정은 아래 좌석 비교 평가를 따라 10/17 부터 뺀다 |
| 배정용 점수(`seat_directional`) | 찾는 사람 → 하는 일 cos | 평균 빼기 + 하는 일끼리 유사도 50% 섞기(`SEAT_CENTER=1` · `SEAT_TOPIC_WEIGHT=0.5`) | 좌석 비교 평가(아래). 예전 방식은 `SEAT_CENTER=0 SEAT_TOPIC_WEIGHT=0`. pair_scores.score 가 표준화 값이 되어 음수도 나온다(콘솔 지표는 상대 비교라 영향 없음) |
| 문장 여러 개 | 한 문장으로 임베딩 | 항목마다 벡터 → 평균 | 짧은 항목 10개 0.73 대 긴 글 1개 0.57, 평균이 최댓값보다 나음 |
| 개인 추천 점수 | min(양방향) | rule 기본(10/18, 위 '추천 10명 점수'). 예전 방식은 `REC_SCORE=min` · `one_way` | 예전 근거는 갈렸음(공동저술 한 방향 0.713 · min 0.694, 스피드데이팅 min 0.538 · 한 방향 0.528). 10/18 가상 평가로 rule |
| 테이블 배정 점수 | min | min 기본, avg · harmonic 선택 | 리허설에서 셋을 비교. pair_scores 에 두 방향 원본을 남긴다 |
| 담금질 | 매번 전체 재계산 | 증분 계산 | 결과는 같고(시험으로 확인) 속도만 다름 |
| 무작위 자리 | 없음 | `random_ratio` (기본 0) | 리허설 정확도가 0.65 미만이면 15~40% 가 이득 |

`EMBED_PREFIX`(접두사)는 `embed.py` 의 `clean_prefix` 로 늘 끝 공백을 하나로 맞춘다 — 빈 값이면 접두사 없음(그대로 `""`), 값이 있으면 공백 하나를 붙인다.
`set -a; . ./.env; set +a` 로 읽으면 `query: ` 의 끝 공백이 버려지는데, `clean_prefix` 가 다시 붙여줘서 docker --env-file 로 읽을 때와 같은 벡터가 나온다(9/30 확인, 안 맞으면 이웃 5명이 78% 만 겹침).

## 행사 흐름과 호출

```
배포 순서: DB 에 0008 → 0009 마이그레이션을 먼저 실행한 뒤 이 서비스를 띄운다(새 칸 · 표를 읽고 쓴다).

행사 전날      POST /precompute {}                      새 코드북 · 전원 주소 · 첫자리 묶음 이름표 초안(운영진 검수) · 테이블토크 배정 · 좌석 초안(1번 교수 · 운영진석 고정, 2~10번 균등) · 전날 추천 목록
체크인 마감    POST /precompute {"reuse_codebook": true}  저장된 코드북으로 현장 등록자에게 주소만 붙임. 테이블토크는 전날 확정이라 다시 배정하지 않음(v0.2 결정 3)
               운영 콘솔에서 공개
포스터 응답 마감 뒤   POST /coffeechat {}                 명함 교환 · 만족도 · 포스터 응답 반영 · 테이블토크 동석자 금지 · 3~4명 그룹 초안 · 근거 한 줄 · 커피챗 버전 추천(커피챗 중 이동 없음, 10/21)
(포스터세션 중)                                           포스터 관심도는 부르는 시점까지 들어온 답만 쓴다. 끝 무렵에 부를수록 많이 반영된다
```

- 운영진(role=staff)도 참가자와 똑같이 주소 · 배정 · 추천에 넣는다. 설문을 비워 두면 점수가 0 이라 사실상 아무 자리에나 앉는다
- 코드북은 `codebooks` 표에 저장하고 행사마다 활성 하나를 둔다(0007). 주소는 다시 학습하지 않는다
- 만족도 반영(3지선다 + 사람 고르기, 답별 가중치 `SAT_WEIGHTS`, 10/6): 많이 얻었어요 1.0 · 조금 얻었어요 0.33 · 잘 맞지 않았어요 −0.2.
  답한 사람의 Seek 를 그 테이블 사람들의 Offer 쪽으로 beta × 가중치만큼 옮긴다(음수면 밀어낸다) → 커피챗 추천에 그 사람들과 비슷한 새 사람이 더 올라온다.
  '이런 분을 더 만나 보고 싶다' 싶었던 동석자를 고르면 테이블 전체 대신 그 사람들 쪽으로 옮긴다. 1초 안에 낸 답은 반영하지 않는다.
  근거: 0.33 은 지수 gain 2^r − 1 (Burges 외 2005), −0.2 는 Rocchio 부정/긍정 비율 0.15/0.75(Manning 외 2008). '잘 모르겠다'는 더 받지 않는다(Krosnick 외 2002).
  조사 전문은 연구 저장소 docs/34.
- 명함 교환 반영(`scoring.card_shift`, 9/29): 명함을 교환한 사람들의 Offer 평균 쪽으로 내 Seek 를 beta(0.5)만큼 옮긴다.
  예전엔 내 Offer 를 옮겼는데, 그러면 명함 한 장에 내 소개가 바뀌고 내 추천은 거의 안 바뀌어서 만족도 · 포스터와 같은 Seek 쪽으로 바꿨다.
  만족도 응답률이 낮아 대체 경로로 가면 만족도와 함께 명함 교환도 반영하지 않는다(예전과 같음)
- 포스터 관심도 반영(`POSTER_WEIGHTS`, 9/29 C안과 같은 규칙): 더 알아보고 싶다 1.0 · 흥미로웠다 0.33 · 내 관심 분야는 아니다 −0.2.
  관심 있게 본 포스터(제목 + 주제 태그 벡터)의 가중 평균 쪽으로 Seek 를 당기고, 관심 없다고 한 포스터 쪽에서는 따로 밀어낸다.
  만족도 응답률과 상관없이 답한 사람마다 반영한다
- 가중치는 문헌 관행(지수 gain, Rocchio)으로 정한 출발점이다. 정확한 값은 문헌으로 못 정해서 리허설 답 분포와 추천 변화를 보고 다시 정한다
- 배정 이유: 두 라운드 모두 `table_members.reason` 에 사람별로 남긴다(테이블, 무작위 자리 여부, 가장 잘 맞는 사람과 점수, 테이블 평균,
  커피챗이면 이전 테이블 · 만족도 · 명함을 교환한 상대 수 · 반영한 관심 포스터 수, 한 줄 설명 text). 운영진 대시보드용이고 참가자 화면에는 안 보낸다
- 만족도 응답률이 `min_response_rate`(기본 0.5) 미만이면 만남 반영 없이 텍스트 점수로만 커피챗을 낸다(대체 경로)
- 요청 본문 선택값: `table_mode`(min · avg · harmonic) · `random_ratio` · `rec_mode`(없으면 `REC_SCORE`) · `beta`
- 코드북 버전 이름은 `cb-<행사>-<날짜시각>`. 배정 버전에 행사 번호(`assign_versions.event_id`)를 남겨 개발 DB 에 행사가 여러 개 섞여도 서로 집지 않는다(0007)
- 실제 개발 DB 한 바퀴(9/26): 가상 68명(sim-minchan) · 전날 2.1초 · 체크인 마감 1.3초 · 커피챗 1.2초 · 재회 0 · 공개 안 함 · dev 공개 배정 영향 없음
- 시험 데이터 정리: `python sim/cleanup_event.py sim-minchan` (세기만) → `--yes` (지우기). dev 는 지우지 못하게 막아 둠
- 한 바퀴 확인: `python sim/make_fake_csv.py sim/fake_70.csv` 다음 `python sim/run_service_sim.py sim/fake_70.csv`
  (맥 CPU, 모델 로드 9초 · 전날 0.9초 · 체크인 마감 0.6초 · 커피챗 0.3초 · 제약 위반 0)
